# Music Request Server — issue register

Audit date: 2026-09-14
Scope: current worktree at HEAD `7163979` plus the changes made while resuming
this task. Existing commits and user changes were preserved.

Status values:

- `NOT FIXED`: observed during this audit; no application fix was made.
- `FIXED`: implemented and verified by a named regression check or a
  documented, reproducible live check.
- `PARTIAL`: the narrow implementation exists, but part of the stated scope
  remains intentionally unimplemented or unverified.

There was no `issues.txt` or `missing.txt` in the repository. `ideas.md` is a
feature backlog, not an issue log, so this file was created without removing or
rewriting any existing issue entries.

## Audit plan and critique

1. Inventory the entry points, configuration/data paths, HTTP routes, and trust
   boundaries.
2. Check persistence, identity, filesystem safety, and process lifecycle paths.
3. Review the current download/casting changes for race conditions and protocol
   correctness.
4. Run the compile, access-check, and self-test paths, then compare their claims
   with what they actually exercise.
5. Record each actionable defect with evidence, impact, and a concrete fix/test
   specification.

The existing route check is not sufficient as a security plan: it verifies that
most routes have *some* dependency, but it does not verify that a route which
changes machine state uses the owner dependency rather than the general-auth
dependency. The current self-test also claims to be read-only/offline while it
executes mutating request paths and reaches the configured LLM. Those are test
design flaws, not evidence that the implementation is safe.

## Findings

### SEC-001 — A guest can mint the owner's full-access pass through the QR endpoint

Priority: P0
Status: FIXED — commit f2ba411, 2026-09-13, deployed and verified live

Resolution: `/api/qr` now requires `Owner`. 17 regression checks added and run
against the vulnerable `Auth` guard first (6 failures: full and phone links got
HTTP 200 and an SVG), then against the fix (all pass). Live server: guest 403,
owner 200. NOT covered by the fix: any owner pass already extracted before
f2ba411 remains valid — the vulnerable path reissued the two existing permanent
owner passes (`REVCd57Z`, `1i3hJxO8`, both `expires=0`). Rotating them is a
separate decision for the owner, since it unpairs their own devices.

Evidence:

- `src/mrs/web/api.py:1923-1938` protects `/api/qr` with `Auth`, not `Owner`.
- The handler calls `sec.owner_pass(key)` when no pass id is supplied, then puts
  the resulting owner credential into `net.addresses(token)` and returns it as
  an SVG QR code.
- A temporary-data test with a normal full guest token received
  `GET /api/qr?kind=lan` as HTTP 200 (`image/svg+xml`); the request also caused
  an owner pass row to be created.

Impact: anyone holding any shared link can read the QR response, extract the
owner pass, and then call every owner-only route. This bypasses the intended
credential boundary and makes all other pass scoping ineffective.

Fix specification:

- Require `Owner` for `/api/qr` unless there is a narrowly defined, separately
  authenticated use case that does not return an owner credential.
- Do not mint or reissue an owner pass during a guest request.
- Add regression tests for full guest, phone guest, expired guest, owner key,
  and owner pass. Guest requests must return 403 and must not modify the pass
  registry.

### SEC-002 — General-auth routes bypass the documented owner/guest isolation

Priority: P1
Status: FIXED (7e94fc1) — verified by test and live. Hijack proven first: corrected check run against the old guard gets HTTP 200 for a phone link sending the shared player to cast:browser.

Evidence:

The code explicitly says that guests should receive only their own settings in
`src/mrs/web/api.py:1253-1262` and correctly enforces that policy in
`/api/settings` and `/api/setting`. Several adjacent routes instead accept only
`Auth` and directly mutate or expose owner state:

- Playback and machine state: `/api/unskip` (`442-445`), `/api/restart`
  (`707-710`), `/api/audio` (`1298-1311`), `/api/audio/devices`
  (`1373-1376`), `/api/audio/device` (`1453-1464`), `/api/theme`
  (`1950-1953`), `/api/announce` (`1956-1959`), `/api/sleep` (`1962-1964`),
  `/api/download` (`1967-1969`), and `/api/pin` (`1972-1974`).
- Owner integrations and persistent credentials: `/api/cookies*`
  (`2351-2420`), `/api/openfolder` and `/api/library/scan` (`2425-2440`),
  `/api/lastfm` (`2456-2466`), `/api/alarms` (`2469-2479`), and `/api/cast`
  (`2482-2491`).
- External-service calls and global model state: `/api/groqmodels` and
  `/api/groqmodel` (`2010-2031`).
- `/api/health` and `/api/diag` also expose machine/service diagnostics to any
  valid guest token.

A direct probe with a full guest token returned HTTP 200 and changed the
  global theme, announce flag, audio normalization/crossfade, alarms, Last.fm
  credentials, and cast peers. The same token could read cookie path, cookie
  health, and installed-browser information. This is separate from the
  intentional ability of a full guest to queue/control the shared player.

Impact: a shared link can change what the owner hears, alter persistent machine
configuration, poison or replace YouTube credentials, close browsers when the
opt-in is enabled, trigger scans, alter external-service settings, or spend
remote API quota. A revoked or short-lived guest link is still too powerful
while it is valid.

Fix specification:

- Use `Owner` for machine, credential, integration, diagnostic, and owner-data
  routes.
- For settings that are intentionally guest-local, require `Request` and write
  through the caller's profile/session, as `/api/setting` does.
- Define a route authorization matrix (`owner`, `shared-player`, `guest-profile`,
  `read-only`) and test every route against owner key, owner pass, full guest,
  phone guest, and revoked/expired credentials. The current dependency-presence
  check is not enough.

### TEST-001 — The access/self-test suite is neither hermetic nor read-only

Priority: P1
Status: FIXED (5f45dcb plus this pass) — checks and self-test run inside `isolated()` + `offline()`: disposable data/cache roots, loopback-only sockets, catalog/request stubs, and explicit offline-attempt detection. Clean CPython 3.12 venv run: 504 checks passed with the new `httpx2` dependency and no Starlette deprecation warning.

Evidence:

- `src/mrs/checks.py:11-15` claims the checks use no network and no mpv.
- `src/mrs/checks.py:1561-1610` posts several requests to the real Shortcut
  endpoint. Those requests call `handle_request`, which can resolve, queue, and
  download music.
- `src/mrs/selftest.py:116-134` calls `/api/theme`, whose GET handler changes
  persistent configuration. The test does not restore the user's theme.
- The checks create profiles/passes and touch the live stores. They remove pass
  rows at the end but do not provide a disposable data directory or reliably
  undo all profile/store side effects.
- Running the checks in this working tree passed 346 access checks but emitted
  Groq HTTP 400/429 traffic. Running the self-test also emitted the same
  external traffic and took roughly 22 seconds. This is direct evidence that
  the “offline” claim is false when Groq is configured.

Impact: CI or an owner running `--check` can consume paid/rate-limited API quota,
depend on remote availability, alter the live queue/configuration, create test
data, and still report a green result. The tests can also interfere with a
currently running player.

Fix specification:

- Run tests with a disposable `MRS_DATA_DIR` and an isolated cache directory.
- Inject or monkeypatch the LLM, catalog, downloader, mpv/player, and request
  handler for the offline suite. Assert that no socket/subprocess download is
  attempted.
- Split hermetic authorization tests from explicit external integration tests.
- Make read-only checks actually read-only; use direct unit calls for mutation
  tests and restore every changed setting/store.
- Add coverage for SEC-001 and SEC-002 rather than only checking that a route
  has a dependency.

Priority: P1

- `README.md:107-113`, `README.md:183`, `README.md:215`, and
  `README.md:395` refer to `app.py`; there is no `src/app.py` in the repository.
  The actual source entry points are `launcher.pyw` and `src/mrs/server.py`.

  not use the application's fallback chain.
- The README documents a Groq default and `history_size` that disagree with the

Impact: a source user following the documented command gets a file-not-found
failure. A user who bypasses that can be sent to the wrong port, can seed a dead

working fallback. This is a release/install blocker, not cosmetic documentation

### DL-001 — Download timeout does not apply while yt-dlp is silent

Priority: P1
Status: FIXED (7e94fc1 plus this pass) — a fake silent child now verifies the 0.1-second deadline, termination/reaping, and removal from the process registry. Included in the final 505-check suite.

Evidence:

- `src/mrs/core/downloader.py:290-334` iterates directly over
  `proc.stdout` and checks the deadline only after a line is received.
- A child process that produced no output for 1.2 seconds, passed to `_run`
  with `timeout=0.1`, took about 1.28 seconds and returned code 0. The timeout
  was therefore not enforced during the silent interval.

Impact: a DNS stall, blocked socket, or hung yt-dlp process can hold a queue
worker indefinitely. The in-memory arriving record and duplicate-request waiters
can remain active, and the UI can report a download that will never finish.

Fix specification:

- Poll the process or read output on a separate thread/queue so the monotonic
  deadline is checked independently of stdout activity.
- Kill the process tree on timeout, reap it, clear both in-flight registries,
  and return a distinct timeout reason.
- Test silent processes, delayed output, a child that ignores termination, and
  duplicate callers.

### DL-002 — Final-name partial downloads can be mistaken for complete files and pruned while active

Priority: P1
Status: FIXED (7e94fc1 plus this pass) — verified that `.part` is not a cache hit, active IDs are protected from pruning, and an exception clears both in-flight registries. A hard process kill/cold-restart integration test is still not simulated; yt-dlp's atomic `.part` publication and age-based stale-part cleanup remain the recovery boundary.

Evidence:

- The current downloader change deliberately uses `--no-part` and writes to
  the final output template (`src/mrs/core/downloader.py:424-436`).
- `Downloader.cached()` (`186-192`) and `cast.source_for()`
  (`src/mrs/core/cast.py:55-63`) treat any file larger than 100 KB as ready.
- The in-flight registry is process memory only. After a restart, a truncated
  final-name file has no marker distinguishing it from a completed download.
- Automatic pruning scans all root cache files (`src/mrs/core/downloader.py:228-265`).
  An active download is not inserted into queue metadata until after completion
  (`src/mrs/core/queue.py:700-730`), so the normal keep-path set does not protect
  it.
- `_fetch_locked` drops the global in-flight record on its expected return paths,
  but an unexpected exception can bypass those calls; `fetch` only clears its
  separate per-instance event (`downloader.py:357-385`).

Impact: a server restart or cache-prune pass can expose/delete a growing or
truncated file. The player or phone can then receive corrupt audio, and an
unexpected exception can leave a permanent `arriving` state for that id.

Fix specification:

- Download to an unambiguous temporary extension/name and atomically rename only
  after successful validation; remove stale temporary files at startup.
- Protect active paths/IDs in the cache cleaner and put `_drop_inflight` in a
  `finally` covering the entire fetch attempt.
- Test cancellation, process crash, restart recovery, prune during download,
  and a download failure raised before the normal return paths.

### CAST-001 — The growing-file HTTP response is not a valid media implementation for all clients/formats

Priority: P1
Status: FIXED (7e94fc1 plus this pass) — regression checks cover full-file `200`, suffix `206`, invalid `416`, multipart ranges, and the content type for all supported native audio extensions. Growing-file serving remains removed. A physical Safari/iOS client check is still unavailable in this test environment.

Evidence:

- `src/mrs/web/api.py:1566-1644` sends a prefix of a file as `206`, invents a
  `Content-Range` total from a yt-dlp progress estimate, and ends the response
  at the current file length. The browser is expected to issue later ranges.
- The range parser mishandles suffix ranges such as `bytes=-500` and does not
  support multi-range requests. A request without a Range header also receives
  `206` rather than a normal complete-file response.
- The partial response always uses `audio/mp4`, even when the source is `.mp3`,
  `.aac`, `.wav`, or another native format.
- Completed non-MP4 output is returned as `application/octet-stream` by
  `api_output_stream` (`1675-1678`), which also prevents reliable media-type
  selection.
- A prefix is not guaranteed to be independently decodable or seekable merely
  because the total byte count is known. Container metadata/fragment layout must
  be valid for the target browser.

Impact: Safari/iOS and other media clients can reject the response, show an
incorrect duration, fail to seek, stop after the first prefix, or refuse to
play a non-MP4 file. The feature is not covered by an integration test against
the actual browser range behavior.

Fix specification:

- Either serve only completed, correctly typed files, or implement a format
  designed for progressive/fragmented delivery and validate it with target
  clients.
- Use a standards-compliant single-range parser, correct suffix-range behavior,
  correct `Content-Type` per extension, and a trustworthy final size. Do not
  advertise a guessed total as final unless the downloader guarantees it.
- Add tests for no range, open-ended range, suffix range, invalid/multi-range,
  every native extension, and a stalled/failed download.

### RUN-002 — Port fallback starts the server on one port while the launcher opens another

Priority: P1
Status: FIXED (7e94fc1 plus this pass) — forced fallback test verifies selection of the next available port, the preferred-port warning state, URL construction, and that launcher actions read the live port.

Evidence:

- `src/mrs/server.py:119-126` deliberately returns a fallback candidate and
  stores the configured value in `runtime["wanted_port"]`.
- `src/mrs/server.py:352-353` records the actual port in `runtime["port"]`.
- Tray and desktop-browser actions in `launcher.pyw:710-715` and
  `launcher.pyw:736-754` continue to build URLs from `config.get("port")`, not
  `srv.runtime["port"]`.
- The server itself logs that links and router forwarding will not reach the
  fallback port, but the launcher does not surface or reconcile that state.

Impact: when the preferred port is occupied, the server can be healthy on the
fallback port while tray actions, desktop opening, and user-facing links still
target the occupied/wrong port. The result looks like a dead server or a bare
404 and can also hit an unrelated process on the configured port.

Fix specification:

- Centralize live-port resolution and use it in every launcher action, local URL,
  QR/link generator, readiness check, and shutdown/handover path.
- Show a clear fallback warning and make the actual port discoverable.
- Add a test that occupies the preferred port, starts the server, and verifies
  every generated URL uses the bound candidate.

### DATA-001 — Local-library IDs change every process because they use Python’s randomized hash

Priority: P1
Status: FIXED (7e94fc1 plus this pass) — normalized deterministic SHA-256 IDs are checked in two fresh Python interpreters; scan also builds a single path index and preserves old local IDs at the same path.

Evidence:

- `src/mrs/core/library.py:84-88` creates IDs with
  `abs(hash(str(path)))`.
- Two separate Python processes produced different hashes for the same path
  during this audit.

Impact: after every restart, the same local file receives a new `video_id`.
History, likes, blocks, dedupe, queue references, and persisted UI selections no
longer identify the same track. The bug is silent because the library still
appears to scan successfully.

Fix specification:

- Derive the ID from a deterministic normalized path (for example a versioned
  SHA-256 scheme), optionally including a file identity/stat component if that
  is desired.
- Define a migration/compatibility rule for existing `local:` IDs.
- Test two separate interpreter processes, path case/separator normalization,
  moved files, and replacement files.

### DATA-002 — Cached profiles/sessions do not reflect pass permanence changes

Priority: P1
Status: FIXED (7e94fc1 plus this pass) — regression test changes a pass temporary→permanent→temporary while its session is live and verifies the cached profile and session are replaced in each direction.

Evidence:

- `src/mrs/core/profile.py:266-279` constructs a `Profile` once and caches it;
  `permanent` is derived only from the first row seen.
- `src/mrs/web/security.py:384-408` can change an expiring pass to permanent or
  a permanent pass to expiring through `extend`.
- `src/mrs/core/session.py:319-329` also caches a `Session`, which retains the
  old profile/taste/queue object.

Impact: extending a temporary link permanently can leave it using the in-memory
neutral/non-persistent profile for the existing session. Converting a permanent
link to temporary can leave it writing to disk. The owner UI says one policy is
active while the running session uses another.

Fix specification:

- Invalidate/rebuild the profile and session whenever pass permanence changes,
  or make the persistence policy dynamic rather than copied at construction.
- Define behavior for an already-playing session and for a pass extended while
  expired.
- Add tests for both transition directions with an existing profile and session,
  including whether prior data is retained or intentionally discarded.

### BACKUP-001 — Windows-style mixed separators can escape the backup restore root

Priority: P2
Status: FIXED (7e94fc1 plus this pass) — a Windows-style mixed-separator member is restored alongside a valid playlist file; the valid file is retained and the sentinel outside the playlist remains unchanged.

Evidence:

- `src/mrs/core/backup.py:104-120` checks `..` only after splitting archive
  names on `/`, then writes `root / n`.
- A crafted archive member such as `playlists/..\\config.json` contains a
  backslash traversal component that the string check does not recognize. On
  Windows, `Path` treats the backslash as a separator and the output resolves
  outside the intended playlist directory, potentially overwriting a root data
  file.

Impact: an owner restoring a malicious or tampered backup can overwrite files
outside the intended archive member directory. The route is owner-only, but the
backup file itself may have come from an untrusted source.

Fix specification:

- Normalize both slash types before validation, reject absolute/UNC/device
  paths, resolve the candidate, and require it to remain under the intended
  data root.
- Bound total uncompressed bytes and per-member bytes to avoid zip bombs.
- Add Windows-style traversal, absolute path, symlink, duplicate-member, and
  oversized-member tests.

### DATA-003 — Spectrum cache filenames collide for different files with the same stem

Priority: P2
Status: FIXED (7e94fc1 plus this pass) — regression coverage confirms same-stem files in different folders and a replaced file map to distinct content-cache paths.

Evidence: `src/mrs/core/spectrum.py:43-45` stores every analysis as
`<Path(path).stem>.bin`, and `analyse()` returns any existing non-empty cache
without checking the full path, file identity, or modification time.

Impact: `Album A/song.mp3` and `Album B/song.mp3` share one visualizer. Replacing
an audio file under the same name also leaves stale spectrum data. This is a
silent UI correctness bug that becomes common as soon as a library has multiple
albums containing the same track name.

Fix specification: hash a normalized full path plus a file version/stat marker,
or store metadata next to the cache and invalidate on mismatch. Add same-stem,
replacement-file, and concurrent-analysis tests.

### DATA-004 — One malformed playlist row can make the whole playlist endpoint fail

Priority: P2
Status: FIXED (7e94fc1 plus this pass) — mixed valid, non-object, wrong-type, invalid-duration, and incomplete rows are covered; malformed rows are logged and skipped without losing valid tracks.

Evidence: `src/mrs/core/playlists.py:101-106` catches file-level JSON errors but
then maps every row directly through `Track.from_dict`; `src/mrs/models.py:159-162`
assumes every row is a mapping and calls `.items()`.

Impact: one hand-edited, partially migrated, or corrupt row can raise an
`AttributeError` and break playlist listing/tracks/queue operations instead of
returning the valid tracks. A user has no repair path through the UI.

Fix specification: validate each row independently, skip and log malformed rows,
preserve valid rows, and expose a repair/export diagnostic. Add malformed-row,
wrong-type, and partial-write recovery tests.

### BUILD-002 — The requested PyPy executable is incompatible with this Windows dependency/build stack

Priority: P2
Status: NOT FIXED AS REQUESTED — the installed PyPy 7.3.20 can run Python 3.11,
but no supported packager in the current stack accepts it, and the Windows
dependency set cannot be resolved unchanged. The installed/restarted release
therefore uses CPython 3.12; it is not represented as a PyPy build.

Evidence: PyInstaller's own compatibility check raises
`ERROR: PyInstaller does not support {sys.implementation.name}. Only CPython is
supported.` See
https://github.com/pyinstaller/pyinstaller/blob/develop/PyInstaller/compat.py#L2780-L2783.
The official Nuitka manual likewise requires CPython, and PyOxidizer's
documented targets are CPython 3.8–3.10:
https://nuitka.net/user-documentation/user-manual.html#python
https://pyoxidizer.readthedocs.io/en/stable/pyoxidizer_getting_started.html#python-requirements
A PyPy `pip --dry-run` against `requirements.txt` also fails at the Windows
`PyAudioWPatch>=0.2.12` dependency (`No matching distribution found`); this
module provides the WASAPI loopback meter and is explicitly collected by the
current spec.

Impact: forcing a PyPy bundle would mean changing the packaging architecture
and dropping or porting the WASAPI listener dependency, then revalidating the
webview/native stack and all release checks. The current CPython executable is
the only verified release artifact.

Fix specification: use CPython with the checked-in PyInstaller spec for the
current release. If PyPy remains a hard requirement, first replace or port
PyAudioWPatch and select a packager/runtime bundle that explicitly supports
PyPy on Windows, then pass the complete install, self-test, and audio-device
acceptance checks before replacing the release pipeline.

### SEC-003 — Sensitive mutations and credentials are exposed through GET query strings

Priority: P2
Status: FIXED (2026-09-13 work plus this pass) — writes are POST+JSON, credentials in `X-Music-Key`, cross-origin POSTs refused, and raw-key URLs are limited to compatibility mode or loopback. New installs are strict; legacy installs migrate deliberately. The 19 focused SEC-003 checks remain green within the 505-check suite. Owner audit is now visible in Settings → System. A real iOS Shortcut using the new POST shape has not been exercised.

Evidence: `allow_key_in_url` defaults to true in `src/mrs/config.py:49-53`, the
README teaches `?key=...` URLs, and multiple mutating endpoints accept secrets or
state changes through GET parameters, including `/api/lastfm`, `/api/groqkey`,
pass creation/extension, cookie import, and machine settings.

Impact: raw keys, pass tokens, Last.fm secrets, and configuration values can land
in browser history, proxy/access logs, Referer headers, screenshots, and link
scanner requests. GET prefetching can also trigger state changes without a clear
user action.

Fix specification: move state-changing actions and secret submission to POST with
appropriate origin/CSRF protection, use headers for owner credentials, default
raw-key-in-URL compatibility off for new installs, and scrub/redact sensitive
query parameters from logs and generated links. Preserve a deliberate, tested
compatibility mode for old Shortcuts rather than making it the default security
posture.

### DATA-005 — Taste writes can be lost, and blocking mutates unsaved state

Priority: P1
Status: FIXED (2026-09-15 audit) — a failed play-stats write remains dirty for
the next flush, block removal runs under the taste lock, block removal is saved
durably, and unblocking no longer performs a second destructive history delete.

Evidence: `TasteEngine.save()` caught a disk/permission/temporary-lock failure
and then unconditionally cleared `_dirty`; the next flush therefore skipped the
retry. `block()` also called `_drop_ids()` outside the lock and never persisted
the resulting play-stat/history deletion. The old block path also ran that
deletion when turning a block off.

Impact: a full or transiently locked disk could silently lose listening history,
and concurrent ranking/player activity could race a block operation. A restart
could restore evidence that the user had blocked, while an unblock could mutate
history unexpectedly.

Fix specification: keep failed writes dirty and retryable, protect taste-state
deletions with the same lock as reads/writes, save the deletion, and only remove
scoring evidence when a recording is newly blocked. Regression checks cover a
failed write, malformed counters, durable block removal, and the complete suite.

### DATA-006 — Corrupt listening state can crash rankings and smart playlists

Priority: P1
Status: FIXED (2026-09-15 audit) — persisted song/artist counters, history,
recent rows, liked rows, and played timestamps are filtered on load; smart-list
count sorting ignores invalid values and tolerates a failing count provider.

Evidence: `play_counts()` converted arbitrary saved values with `int()` and
`_smart_rows()` converted them again while sorting. A row such as
`{"video_id":"x","plays":"not-a-number"}` made the most-played endpoint
raise `ValueError` and return a server error instead of omitting one bad row.

Impact: hand-edited or partially corrupted state could make radio/cache ranking
or the dynamic playlist panel fail for the whole listener.

Fix specification: validate count rows at the persistence boundary and treat
invalid dynamic-playlist counts as absent. Keep valid sibling rows available.
The issue-regression section includes a mixed valid/corrupt state and a broken
most-played provider.

### DATA-007 — One malformed local-library row discarded the entire index

Priority: P1
Status: FIXED (2026-09-15 audit) — the library index now validates and skips
bad rows individually while retaining valid local tracks.

Evidence: `_load()` used one list comprehension inside one broad `try`. A single
non-object row or invalid field raised and replaced the whole in-memory library

## Implementation plan for the requested change

The defect list is broad enough that a single ad-hoc patch would make the
system less reliable. The work is therefore staged around shared boundaries:

1. `DONE`: establish one authorization policy table and use it for owner-only routes;
   move secret/state mutations behind POST and add compatibility tests for
   legacy callers.
2. `DONE`: make tests hermetic before using them as a safety net: disposable data and
   cache roots, dependency injection for network/LLM/download/audio work, and
   explicit external-integration tests.
3. `DONE`: repair download lifecycle and media serving together: timeout independent of
   stdout, temporary files plus atomic completion, active-file protection, and
   standards-compliant completed-file/range responses.
4. `DONE`: repair durable identity and persistence: deterministic local IDs, live
   profile/session policy, safe backup extraction, collision-free spectrum
   caches, malformed-row tolerance, and dependency/docs/setup drift.
5. `DONE`: implement announcement volume as an audio policy rather than a percentage
   hack: preserve the music mixer level, apply configurable dB ducking, use
   the same base level for speech, serialize overlapping announcements, and
   restore state in all exit paths.
6. `DONE`: add the researched, local features that fit existing boundaries:
   an owner audit trail, listener-scoped smart playlists, periodic library
   refresh, and the already-landed AutoEq headphone correction. Larger
   integrations such as ListenBrainz, hardware transcoding, and per-client
   bitrate negotiation remain follow-up items.

Plan critique: implementing broad integrations before fixing the auth and
download boundaries would multiply the attack surface and make failures hard
to attribute. The selected additions are local, testable, and useful without
introducing a new service dependency; the integration ideas are recorded
instead of pretending that a shallow adapter is production-ready.

## Research notes used for scope

- yt-dlp documents `.part` files as the default and provides separate temporary
  and final paths, so the downloader should retain an unambiguous temporary
  name and publish the final name only after success:
  https://github.com/yt-dlp/yt-dlp#filesystem-options
- RFC 9110 defines single-range responses, suffix ranges, `206`, `416`, and
  `Content-Range`; the server should follow those rules and should not invent a
  final size for a still-growing file:
  https://www.rfc-editor.org/rfc/rfc9110.html
- mpv exposes an internal mixer volume and a separate `volume-gain` dB control;
  this is the correct primitive for configurable narrator ducking rather than
  multiplying a percentage:
  https://mpv.io/manual/stable/
- Navidrome’s documented feature set makes smart/dynamic playlists, library
  monitoring, scrobbling, sharing, and per-user controls common expectations
  for a self-hosted music server:
  https://www.navidrome.org/docs/overview/
- Jellyfin documents client capability profiles and user policies such as
  library access, bitrate limits, and transcoding permission. These are useful
  follow-up directions, but this codebase needs a capability/policy boundary
  before they can be added safely:
  https://jellyfin.org/docs/general/post-install/transcoding/
- AutoEq publishes measured headphone response data and correction profiles;
  this project caches the selected profile, applies it per Windows output, and
  asks before using ambiguous device-name matches:
  https://github.com/jaakkopasanen/AutoEq

## Continued defect audit — 2026-09-20

### SEC-004 — A guest `GET` can perform an unbounded AutoEq network fetch and persistent write

Priority: P2
Status: FIXED — 2026-09-20. Resolution: AutoEq profile warming is POST-only in
strict mode; compatibility GETs are cache-only, guest work is metered, writes
are atomic, and the profile cache is capped at 128 files.

Evidence: `/api/autoeq/profile` is listed in `READ_ONLY` in
`src/mrs/web/policy.py`, so the request middleware accepts
`GET /api/autoeq/profile?id=...` even with legacy GET mutations disabled.
The handler in `src/mrs/web/api.py` calls `autoeq.profile(id)`. On a cache
miss, `src/mrs/core/autoeq.py:profile()` downloads the selected profile from
GitHub and writes it to `MRS_DATA_DIR/autoeq/profiles/`. The route has no
per-pass rate or storage bound. An isolated regression probe confirmed that
the policy treats the request as read-only while one GET invokes `_fetch` and
creates the profile file.

Impact: any holder of a valid shared link can use what the application calls a
read-only GET to make the server perform remote requests and permanently fill
the profile cache. This also bypasses the POST/JSON-only mutation boundary that
the security policy is intended to enforce; browser prefetching and crawlers
can trigger the same work unintentionally.

Fix specification: a GET must only report an already-cached profile (or a
not-ready result) and never initiate a download or write. Move cache warming to
an explicit POST operation, meter it by pass/account, and bound/prune the
profile cache. Add coverage that a cache-miss GET makes no fetch and no file,
while an authorised POST performs exactly one bounded warm.

### DATA-008 — Account updates lose data when two server processes share a data directory

Priority: P1
Status: FIXED — 2026-09-20. Resolution: every account read-modify-write now
holds a conservative inter-process file lock as well as the in-process lock.
Two isolated Python processes admitting different identities retain both rows.

Evidence: `src/mrs/web/accounts.py` protects `_read()` → mutation → `_write()`
only with a process-local `threading.RLock`. The file is atomically replaced,
but there is no lock spanning that whole read-modify-write transaction across
processes. A deterministic two-process probe paused both `accounts.admit()`
calls after they read the same empty `accounts.json`, then released them to
write distinct Google subjects. Both exited successfully, but the final file
contained only `useralpha`; `userbravo` was silently discarded.

Impact: starting a second copy during an upgrade, recovery, or diagnostic run
can silently erase a newly admitted account or overwrite a concurrent scope,
last-seen, or forget operation. Atomic file replacement prevents malformed
JSON, not lost updates.

Fix specification: add an inter-process lock that covers each account
read-modify-write transaction (`admit`, `seen`, `set_scope`, and `forget`),
or move accounts to a transaction-capable store. Keep the existing in-process
lock, make stale-lock recovery conservative, and add a two-process regression
test that admits two identities at the same time and retains both rows.

### DATA-009 — Concurrent configuration saves still discard unrelated settings

Priority: P1
Status: FIXED — 2026-09-20. Resolution: config read/merge/replace is one
inter-process transaction, including concurrent first-run bootstrap. A
two-process probe preserves independently written `theme` and `volume` keys.

Evidence: `src/mrs/config.py:Config.save()` re-reads `config.json` and merges
only this process's dirty keys, but the read and subsequent atomic replacement
are protected only by the process-local `_lock`. Two independent processes can
therefore read the same base document, each build a correct-looking merged
document, and then overwrite one another. A deterministic probe paused both
processes immediately before `write_atomic`: one set `theme` to `audit-dark`,
the other set `volume` to `13`. Both returned success; the final configuration
had `theme: audit-dark` and the old `volume: 70`.

Impact: a second instance, updater, recovery process, or diagnostic tool can
make legitimate settings changes vanish without warning. This is especially
dangerous for security and connectivity settings because the UI reports its
own successful write even when a different process immediately discards it.

Fix specification: hold an inter-process lock from the on-disk read through
the atomic replacement, then refresh the losing process's in-memory view from
the committed document. Do not solve this with a fixed temporary filename or
best-effort retry. Add a two-process test that commits disjoint settings at the
same time and asserts both values survive, plus a deliberate same-key conflict
test with defined last-writer/conflict behavior.

### DATA-010 — An interrupted like or block save destroys the entire preference file

Priority: P1
Status: FIXED — 2026-09-20. Resolution: likes and blocks are snapshotted under
their lock and written atomically, preserving the prior parseable file on a
failed replacement.

Evidence: `src/mrs/core/taste.py:_save_liked()` and `_save_blocks()` write
directly to `liked_songs.json` and `blocked_music.json` with `Path.write_text`
instead of the repository's `write_atomic()` helper. The exceptions are logged
but the now-truncated file is retained. In an isolated probe, a valid
`liked_songs.json` containing `keep-this-like` was truncated to `[` during a
simulated interrupted save; a fresh `TasteEngine` then correctly rejected the
invalid JSON but recovered an empty like list. The same direct-write pattern is
used for the persistent block list.

Impact: a power loss, disk-full condition, antivirus/file-lock failure, or
process termination at the wrong moment can erase every saved like or every
"never play this" block. The application continues with an empty preference
set, so the loss can be mistaken for a normal change rather than a recoverable
storage failure.

Fix specification: snapshot the lists under the existing lock and persist both
files with `write_atomic()`; retain the previous parseable file on every failed
replacement. Add fault-injection tests for likes and blocks that fail after
the temporary file is written and assert a new `TasteEngine` still loads the
last committed data.

### SEC-005 — A shared link can make unlimited paid lyric-identification requests

Priority: P1

### SEC-006 — A shared link can launch unlimited multi-source catalog searches

Priority: P1
Status: FIXED — 2026-09-20. Resolution: catalog search is POST-shaped in

Evidence: `/api/search` is authenticated but never calls `_guard_rate()`.

### API-001 — Non-finite pass lifetimes turn valid owner requests into HTTP 500

Priority: P2
Status: FIXED — 2026-09-20. Resolution: API and security-layer validation
reject NaN, infinities, negative values, and values over one year before pass
expiry arithmetic; zero remains the explicit permanent-link value.

Evidence: `/api/passes/new` accepts `hours: float` and passes it directly to
`security.issue()`. `/api/passes/extend` passes the same unvalidated value to
`security.extend()`. Python and the request validator accept the non-finite
values `NaN` and `Infinity`; both security functions then evaluate
`int(time.time() + hours * 3600)`, which raises instead of returning a client
error. Isolated owner-authenticated probes sent JSON `{ "hours": "nan" }`
and `{ "hours": "inf" }`; both pass creation and extension returned HTTP 500.

Impact: malformed or automated owner input can produce an unhandled server
exception and a generic failure page. This is also a bad boundary for a
credential-minting route: non-finite values must never reach expiry arithmetic
or be able to leave a partially-created pass record.

Fix specification: reject non-finite lifetimes with a 400/422 response before
calling the security layer, define an explicit maximum lifetime, and test
`NaN`, positive infinity, negative infinity, negative values, zero, and a
normal finite lifetime. The failure tests must also assert that no pass row was
created.

### BACKUP-002 — An interrupted restore leaves the live data file truncated

Priority: P1
Status: FIXED — 2026-09-20. Resolution: archives now fully validate and stage

### SEC-007 — A shared link can start unmetered cast conversions

Priority: P1
Status: FIXED — 2026-09-20. Resolution: warm and direct-stream conversion
paths reserve the pass budget before work starts, and the cast engine permits
at most three distinct ffmpeg jobs globally while coalescing duplicates.

Evidence: `/api/output/prepare/{video_id}` is a state-changing route that

### SEC-010 — Public OAuth starts allocate unbounded in-memory state with quadratic work

Priority: P1
Status: FIXED — 2026-09-20.

Resolution: pending OAuth state is capped at 128 globally and 8 per client
address; expiry cleanup is therefore bounded even during abuse.

Evidence: every unauthenticated request to `/auth/google/start` reaches
`google.start()` after the public-admission rewrite. It inserts a six-field
record into the process-global `_PENDING` dictionary for ten minutes. There
is no per-client limit, global cap, or queue bound. Before every insertion it

increasingly expensive O(n) work per request. An isolated configured-Google

Fix specification: restore invitation-bound OAuth starts, enforce a small
per-IP and global in-flight-state limit, and reject excess starts before
allocating state. Expire entries with a bounded structure (for example an
expiry queue) rather than scanning the whole dictionary on every request.
Add stress tests that prove a capped number of states, correct expiry, and
that one client cannot starve another client's legitimate sign-in.

arbitrary media-fetch client against loopback, LAN, file, or protocol-handler

directly returned, this enables internal service probing and can expose local
media through the shared output, trigger unwanted network authentication, or
make the server connect to attacker-controlled endpoints. The guest request
quota limits volume but does not make the trust-boundary violation safe.

Fix specification: never accept a free-form stream URL from a shared client.
Give radio-directory results an opaque, short-lived server-issued identifier
and resolve it server-side, or strictly allow only vetted `https` stream URLs
from recently returned directory entries after DNS/IP validation that rejects
loopback, private, link-local, file, SMB, and redirect-bypass destinations.
Add security tests for private HTTP, `file:`, UNC/SMB, non-HTTP schemes, and
an unrecognised public URL.

### DATA-014 — A failed backup could appear as a usable archive

still had the normal backup name and could later be selected for restore.

Resolution: backup generation now writes to a same-directory temporary file
and atomically publishes the final archive only after the ZIP is closed.
Failures remove only the temporary file and leave existing backups untouched.

### PRIV-001 — Failed pass-profile wipes were reported as successful forgetting

Resolution: profile wiping now retains its in-memory profile until filesystem

### DATA-016 — Playlist deletion could report success after doing nothing

Priority: P2
Status: FIXED — 2026-09-21.

Resolution: deletion now addresses the already-existing, validated folder
without creating one, propagates filesystem errors as `ok: false`, and the

### DATA-017 — Different playlist names could resolve to the same directory

Priority: P1

Resolution: new playlist folders use a stable digest suffix whenever a label

### BOOT-001 — Failed start-at-sign-in changes were saved as enabled

### DATA-018 — Playlist reads and failed operations created phantom folders

Priority: P2
Status: FIXED — 2026-09-21.

Evidence: playlist reads (`tracks`, credits, and shared-state checks) reused
the writer helper `folder()`, which creates its directory. Thus a read-only

### DATA-019 — Interrupted offline playlist copies could be promoted as complete audio

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: playlist offline download copied audio directly to its final
filename. A copy failure can leave that filename containing only a prefix of
the source; on the next pass, `dest.exists()` skipped copying and the code
saved that partial path into `tracks.json` as though it were complete.

Resolution: each playlist copy now goes to a unique same-directory `.part`
file and is atomically replaced into place only after copying succeeds. A
`.complete` marker is written after publication; unmarked files are retried
instead of trusted. Regression coverage forces a partial copy failure, then
verifies no final file or completion marker survives and that a retry safely
publishes the complete source.

### TEST-001 — The packaged HTTP smoke test contradicted the configured link policy

Priority: P2
Status: FIXED — 2026-09-21.

Evidence: the self-test always minted an ordinary shared pass and required

refuses ordinary shared passes when `allow_shared_links` is disabled, which is
the default isolated-test configuration. Consequently, a healthy default

Resolution: the smoke test now uses the non-owner internal player credential

### DATA-020 — Background playlist downloads could overwrite newer list changes

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: `download_async()` checked and added the in-progress name without a
lock, allowing duplicate jobs to start. Each job later saved the complete
track snapshot it read at the beginning. Removing a track while its audio was
copying made the final save put the track back; deleting the list could make
the final writer recreate its directory and index.

Resolution: download names are now claimed under the playlist lock before a
thread starts. Completed paths are merged only into the then-current index,
and no save occurs if that index has been removed. Per-track download failures
also leave the rest of the list running and always reset the activity state.
Regression coverage removes a track and deletes the list between snapshot and
commit, verifying that neither operation is undone.

### DL-004 — Main cache readers ignored the downloader completion marker

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: the downloader wrote `<audio>.complete` only after yt-dlp had
published the final filename, but both `Downloader.cached()` and the cast
source lookup accepted any non-empty final-looking filename without checking
that marker. A crash after yt-dlp's rename and before marker publication could
therefore make the next server process play or transcode an incomplete file.

Resolution: normal downloader and cast cache reads now require the completion
marker. The download worker clears unmarked ordinary-cache files before asking
yt-dlp to retry, finds a just-produced file only within that ordinary cache,
and refuses to return it if marker publication fails. Regression coverage
verifies that an unmarked final name is invisible to both readers until it is
explicitly marked complete.

### RACE-001 — Event-stream reconnects could race a worker publishing sticky state

Priority: P2
Status: FIXED — 2026-09-21.

Evidence: `EventBus.subscribe()` added the new queue under its lock, released
it, then iterated `_latest.items()`. Worker threads call `publish()` and
mutated `_latest` without that lock. A page reconnect concurrent with any
sticky status, queue, or settings publication could therefore raise
`RuntimeError: dictionary changed size during iteration` before the SSE stream
was established.

Resolution: sticky writes and the subscriber's replay snapshot now use the
same lock. The queue receives a stable copy after registration, and a
regression check verifies the replay contract.

### SEC-019 — Elevated Windows startup-task construction did not quote PowerShell literals

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: before-sign-in setup interpolated the executable path, launcher
arguments, Windows username, temporary script path, and task name into
PowerShell single-quoted strings. An apostrophe in an ordinary name such as
`O'Connor` broke the script; in a privileged UAC flow, treating that value as
code rather than data was also an unnecessary command-injection boundary.

Resolution: privileged command construction now uses one PowerShell literal
encoder that doubles embedded apostrophes. It is used for every dynamic value
passed to `Start-Process` and ScheduledTasks, and regression coverage locks
down the escaping rule.

### DOS-001 — Public desktop-download rate tracking could grow without bound

Priority: P2
Status: FIXED — 2026-09-21.

Evidence: `/download/client` kept a one-hour list for each remote IP in
`_DL_SEEN`. Its cleanup ran only when the dictionary already exceeded 512
entries and removed only stale addresses. A burst of distinct current
addresses therefore removed nothing and could grow the process's memory for
as long as public traffic continued.

Resolution: the rate limiter now removes stale rows on every reservation and,
when full, evicts the oldest current address before accepting a new one. Each
active address still receives its own hourly cap, while the public tracker is
strictly capped at 512 rows; regression coverage fills the table and verifies
that the next address does not expand it.

### DOS-002 — Failed-key and ban maps could retain unbounded attacker-controlled IPs

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: every remote wrong key created a `_strikes` row, and every third
wrong key created a persisted `_until` ban row. Neither map had a capacity;
expired bans that were never queried again also remained resident. A
distributed scanner could consequently grow memory and `blocked.json` without
limit simply by rotating addresses.

Resolution: strike and ban stores now expire old bans during failed-key
handling and cap each map at 2,048 entries, evicting the least useful oldest
entry when necessary. Regression coverage fills both tables and verifies a new
address is admitted without expanding either map.

### DL-005 — Cache filenames could collide or return a prefix-matched recording

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: cache IDs were built by replacing every filename-invalid character
with `_`, so distinct source IDs such as `source?one` and `source:one` mapped
to the same file. Cache discovery then used a `source.*` glob without
requiring an exact filename stem, so a request for `source` could accept
`source.more.m4a`. The cast module also duplicated a different sanitisation
rule, making its view of a cache entry disagree with normal playback.

Resolution: non-ordinary or Windows-invalid IDs now receive a stable SHA-256
suffix after the readable portion, cache scans require the exact derived stem,
and casting delegates source lookup to the downloader. Regression coverage
creates collision- and prefix-shaped IDs and verifies each playback path gets
only its own marked audio file.

### CAST-003 — Casting still used raw source IDs as Windows output filenames

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: after cache lookup was made safe for IDs containing filename-invalid
characters, `_converted()` and conversion job names still embedded the raw ID.
An ID such as `source?one` could therefore be downloaded and played from the
cache but fail when ffmpeg tried to create its cast output. Cleanup also tried
to resolve the transformed filename as though it were the original ID.

Resolution: cast output and conversion job names now use the downloader's
canonical cache leaf. The downloader exposes an exact completed-leaf check
for cast cleanup, so a valid transformed source retains its transcode while
an evicted source still removes it. Regression coverage verifies that the
cast output has no invalid characters and survives pruning while its source
is complete.

### RACE-002 — A guest session could start after it had been closed

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: `Sessions.for_pass()` registered a new room, released the session
lock, then called `start()`. A concurrent `close()` could remove and stop that
room in the gap. The first caller then started its queue and heartbeat anyway,
leaving background work running for a session no longer present in the
registry and unable to be stopped by a later close.

Resolution: room activation and the initial touch now occur while the session
registry lock is held, making registration and activation one transaction.
The close operation can only run after activation, at which point it sees and
stops the registered room. Regression coverage blocks activation, attempts a
concurrent close, and verifies it cannot complete until the room is live.

### RACE-003 — An in-flight worker could append to a stopped queue

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: `QueueManager.stop()` only set the worker-loop stop event. A worker
already inside `_process()` could finish a cache hit or download afterwards
and load the track into its sink. Closing a guest session could therefore
leave its now-unregistered queue consuming audio/download work, while process
shutdown could still mutate the owner's stopped queue.

Resolution: stopping a queue now invalidates its work generation, clears
pending state, cancels only that queue's downloader lane, and `_process()`
rejects work both before it begins and immediately before it touches the sink.
Regression coverage blocks a fetch, stops the queue, releases the fetch, and
verifies no track is appended.

### HTTPS-001 — HTTPS gateways/tunnels had no compatible origin mode

Priority: P1
Status: FIXED — 2026-09-21.

Evidence: the server could either speak direct TLS from a local certificate or
plain HTTP publicly. It had no mode for a local gateway/tunnel that terminates
public HTTPS. Sending a gateway to `https://127.0.0.1:<port>` while the app

required `http://127.0.0.1:<port>` gateway origin. Direct certificate mode
remains the default and keeps untrusted proxy headers disabled. Regression
checks cover mode validation, HTTPS URL derivation, and gateway callback URI
generation.
